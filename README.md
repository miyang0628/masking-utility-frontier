# Masking–Utility Frontier for External LLM Coding Assistants in Regulated Environments

A reproducibility harness that quantifies the trade-off between **knowledge-asset protection** and **development utility**
when real source code is sent to an external LLM coding assistant through a reversible-masking bridge, under a regulated
(non-processing) constraint on personal data.

> **Anonymized for peer review.** This repository is prepared for **double-blind** submission to an anonymous venue.
> All author, affiliation, and funding information has been removed. Please do not attempt to de-anonymize.
> Authorship: **Anonymous Author(s)**.

## Summary

The study reframes the security-vs-efficiency debate as a measurable **Pareto frontier**: as masking becomes more
aggressive, reconstruction risk falls while utility also falls. A regulatory **non-processing threshold** (residual
regulated-PII leakage must stay below a bound) is overlaid as a hard constraint on the frontier.

Headline results from the included run (deterministic corpus, `seed = 42`; parametric adversary unless an API key is set):

- A PII/secret-only masking tier already reaches **full recall of injected regulated tokens** (regulatory-compliant)
  while **retaining near-full utility** — but **reconstruction risk for the code's logic stays maximal**.
- Protecting the knowledge asset (reducing reconstruction risk) requires **sacrificing utility**; the identifier-masking
  tier is the visible **knee** of the frontier.
- Compliance and knowledge-protection are **separate axes**: the first is satisfied cheaply, the second is the real
  trade-off.

## Reproduce

Requires Python 3.10+.

```
pip install -r requirements.txt
```

Run the notebooks **in order** (01 → 04), e.g. headless:

```
jupyter nbconvert --to notebook --execute --inplace notebooks/01_generate_synthetic_corpus.ipynb
jupyter nbconvert --to notebook --execute --inplace notebooks/02_masking_and_recall.ipynb
jupyter nbconvert --to notebook --execute --inplace notebooks/03_utility_and_risk.ipynb
jupyter nbconvert --to notebook --execute --inplace notebooks/04_pareto_frontier.ipynb
```

- **Notebook 01 needs network on first run** to fetch the pinned upstream source from GitHub; it is cached under
  `data/_fineract/` afterwards.
- Outputs are written to `results/figures/` and `results/tables/`. The pipeline is deterministic.

## Carrier corpus (real OSS)

The corpus is built from real **Apache Fineract** source (`apache/fineract`, Apache-2.0), pinned at commit
`e0ae48b391ab1b31b597e5fcaeee4a4419e1841a`. Notebook 01 fetches a sparse, shallow copy at that commit and selects a
deterministic sample of source files. The upstream code is **not redistributed** in this repository (it is fetched at
run time and gitignored). Real code provides realistic identifiers and logic for the utility and reconstruction
measurements.

## The reconstruction adversary (real LLM, optional)

Reconstruction risk is measured by an adversary that tries to recover **masked code identifiers** from context; the
recovery rate is the risk. `adversary()` in notebook 03 issues real **OpenAI Chat Completions** calls when an API key is
present, with on-disk response caching for deterministic, free re-runs. Three model tiers act as the adversary-strength
sweep.

Risk estimates are reported as the mean per-file recovery over `N_ADV_FILES = 50` sampled files with **95% bootstrap
confidence intervals**; per-file recovery values are written to `results/tables/risk_samples.csv` for auditing, and the
CIs are drawn on the reconstruction-risk and Pareto figures.

Configure via a `.env` file in the repository root (one level above `notebooks/`):

```
OPENAI_API_KEY=sk-...          # leave as None to use the parametric fallback
LLM_MODEL_WEAK=gpt-4o-mini
LLM_MODEL_MID=gpt-5.4-mini
LLM_MODEL_STRONG=gpt-5.4
```

Copy `.env.example` to `.env` and fill in the key. **`.env` is gitignored; never commit a real key.** With no key, the
notebook falls back to a documented parametric model and labels the run accordingly (`mode = parametric`).

## Data statement

**No real or proprietary sensitive data is used.** Injected sensitive tokens (resident-registration numbers, card
numbers, accounts, secrets, emails, phones) are randomly generated; where a format carries a checksum (card via Luhn,
resident-registration number), the checksum is made valid **only** so detectors can be exercised. No value corresponds
to any real person, account, card, or credential. The carrier code is public open source.

## Scope and limitations

- **Utility is a proxy** (retained functional structure), not a measured success rate of real coding tasks.
- **Reconstruction risk** is measured by the LLM adversary when enabled, otherwise a documented parametric model.
- **Recall is 1.0 and precision is 1.0 on this corpus** because detectors match the injected token formats and the
  carrier code contains no colliding patterns; on harder/obfuscated inputs recall falls below 1, and **measuring that
  gap is the purpose of the method**.
- Open-source code differs in distribution from proprietary code, so absolute values are illustrative; the intended
  reading is **relative comparison across tiers** and the **existence of the threshold**.
